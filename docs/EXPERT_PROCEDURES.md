# Inventaire des procédures expertes et couverture Cartomize

État des sources examinées : **Cartomize 1.4.0**, le **26 octobre 2026**. Base du dépôt avant compléments : `ad4d1d7a89557e347b9a322f73c32205807c077a`.

L’inventaire comprend **123 procédures** : **11 disponibles dans un périmètre explicite**, **48 partielles** et **64 absentes**. Ces nombres décrivent des workflows experts, pas le nombre d’outils du logiciel. Le [registre JSON](EXPERT_PROCEDURES.json) conserve les 123 identifiants d’origine, les fonctions vérifiées, les limites, les conditions, l’ordre proposé et les 88 références de l’inventaire.

## Portée et lecture des statuts

Le diagnostic porte sur les fichiers sources de la version 1.4.0 et les interfaces effectivement raccordées. Le module **M07** ferme désormais le parcours automatique d’imagerie : seuil de couverture appliqué, sélection/mosaïque, compléments STAC bornés, calibration/masques et diagnostics persistants. Voir le [contrat complet](IMAGERY_AUTOMATIC.md). Les modules **M01 à M06 sont implémentés** : couverture des images, workflows vectoriels, statistiques/emprises raster, identité des classes, raccordement des itinéraires et installation commune Python/Jupyter/fenêtre. Les validations M01–M06 sont conservées dans le [rapport historique 1.3.0](VALIDATION_1.3.0.json) ; la validation de M07 figure dans la [note 1.4.0](RELEASE_1.4.0.md). Le commit de base ci-dessus identifie le point de départ du travail, pas un commit final de publication. Les contrôles GitHub Actions et la publication distante restent distincts de cette validation locale.

| Statut | Sens |
|---|---|
| **Disponible** (`available`) | Le cœur de la procédure est réalisable avec les opérations présentes dans le périmètre explicite ; aucun bloc analytique nécessaire à ce périmètre n’est identifié comme manquant. |
| **Partiel** (`partial`) | Une ou plusieurs étapes analytiques réelles sont présentes, mais les compléments listés sont nécessaires au workflow expert complet ou à sa fiabilité. |
| **Absent** (`absent`) | Aucun moteur dédié ni enchaînement suffisamment spécifique ne réalise la méthode ; les seuls outils génériques ne sont pas comptés comme une implémentation. |

Les sources QGIS, ArcGIS, GRASS, organismes producteurs et méthodes décrivent les opérations de référence. Elles ne prouvent pas une implémentation dans Cartomize : celle-ci est reliée aux fonctions du dépôt dans chaque ligne. Une expression raster programmable n’est pas comptée comme un modèle RUSLE, une régression ou un moteur radar. Une maquette cartographique n’est pas une analyse de fragmentation. Aucune parité globale QGIS/ArcGIS n’est revendiquée.

Les fonctions sont nommées avec leur **module de définition**. Plusieurs sont également exportées directement, par exemple `cartomize.audit_imagery`, `cartomize.join_attributes` ou `cartomize.hydrology`. Les identifiants de `capabilities.*.operators` dans le JSON désignent les opérations du registre commun aux chaînes, à `cartomize process` et à la fenêtre. Une liste vide signifie qu’aucun opérateur direct n’est recensé pour cette fonction ; elle peut servir à construire les entrées ou être appelée par une autre opération. [API publique](../src/cartomize/__init__.py), [registre](../src/cartomize/processing.py), [guide des chaînes](PROCESSING.md).

## Ordre d’implémentation proposé

Les corrections de fiabilité M01 à M05, l’intégration M06 et le parcours d’imagerie M07 sont inclus. Les extensions E01 à E07 constituent un ordre de travail proposé, à découper ensuite en petits modules avec leurs données de référence ; ce ne sont pas des fonctionnalités annoncées comme livrées.

Les contrats désormais présents sont explicites. Les statistiques zonales appliquent par défaut scale/offset, conservent un mode brut, calculent la couverture sur toute la zone et stabilisent les contacts avec les frontières polygonales indépendamment des blocs. Les classes numériques équivalentes sont reconnues sans confondre textes, nombres et booléens ; les grilles tournées sont prises en compte à l’échantillonnage. Le routage projette par défaut sur les arêtes et retourne un Point valide pour un trajet réseau nul. [Statistiques raster](RASTER_STATISTICS.md), [classification](../src/cartomize/classification.py), [routage](../src/cartomize/routing.py).

M03 utilise aussi les quatre coins affines des rasters dans `analyze_relations` et protège le fichier d’entrée `valid_footprint` contre l’écrasement. L’analyse de relations reste une comparaison d’emprises totales ; le diagnostic d’images distingue, lui, emprise, données présentes et données utiles. M01 tient également compte de la résolution native des grilles tournées et traite une date vide comme inconnue, avec les mêmes contrôles de mélange de dates. [Relations](../src/cartomize/relations.py), [protection des sources](../src/cartomize/nodata.py), [diagnostic](IMAGERY_AUDIT.md), [préparation](../src/cartomize/imagery.py).

Ces corrections ne suffisent pas à compléter toutes les procédures : G19 attend encore les surfaces par classe et par zone, RS10 les outils de conception de blocs spatiaux et de recherche de paramètres, et SA15 les coûts de temps et restrictions. Leurs statuts restent donc partiels.

## Correspondance exhaustive

Le périmètre de RS01–RS02 est désormais relié à `preprocess_imagery` et à l’opérateur `imagery.preprocess` ; le [guide M07](IMAGERY_AUTOMATIC.md) décrit leurs contrôles de couverture et de catalogue. Leurs statuts étaient déjà disponibles dans un périmètre plus étroit : les totaux de 123 procédures ne changent pas. Chaque identifiant de l’inventaire apparaît une fois. La colonne de droite distingue le complément attendu, les conditions de calcul et la prochaine étape proposée. Les liens Rxxx renvoient aux sources d’origine ; leurs notices complètes sont dans le JSON. Une procédure « disponible » peut nécessiter un enchaînement explicite et une validation experte des paramètres.

## Maintenir cet inventaire

Pour modifier un statut, vérifier le comportement sur une référence métier, mettre à jour les étapes couvertes et manquantes, puis vérifier les chemins et les symboles cités. La présence d’une entrée d’interface ou d’une dépendance ne suffit pas. Conserver les identifiants G01–G28, RS01–RS34, TH01–TH30, SA01–SA28 et EC01–EC03 afin que les évolutions restent comparables.

Le JSON porte les définitions, les totaux, la correspondance API/opérateurs, le prochain module et les URL de référence. Il ne remplace pas `operation_catalog()` pour connaître les paramètres exécutables. Le présent document résume exactement les mêmes 123 enregistrements.
